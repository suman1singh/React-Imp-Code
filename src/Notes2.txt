Rendering a large dataset like 10,000 records efficiently in a 
React app can be challenging, but there are several strategies you 
can use to improve performance and avoid blocking the UI.

1. Lazy Loading (Pagination)
Instead of fetching and rendering all 10,000 records at once, 
fetch them in smaller chunks, and render them as needed. 
This can be done using pagination or infinite scrolling.

Pagination: Load a fixed number of records per page, like 20 or 50, and 
allow the user to navigate between pages.

Infinite Scrolling: Load a batch of records when the user scrolls near the 
bottom, keeping the UI smooth.

#### GraphQL with React.js: A Complete Guide ####
==>What is GraphQL?
GraphQL is a query language for APIs that allows clients to request only the specific data they need from a single endpoint. 
It eliminates over-fetching and under-fetching of data, making APIs more efficient.
With React.js, GraphQL is often used with libraries like Apollo Client to manage queries, mutations, and caching.

==>Why Use GraphQL with React?
1. Single Request, Multiple Resources: No need to call multiple REST endpoints.
2. Dynamic Queries: Clients request only the specific data they need.
3. Real-Time Updates: Get live updates using subscriptions.
4. Easier to Maintain: No need for API versioning.

==>How to Set Up GraphQL with React.js
Step 1: Install Required Packages
Install the following libraries:
npm install @apollo/client graphql
Step 2: Create Apollo Client
Create an Apollo Client instance to connect to the GraphQL server.

// apolloClient.js
import { ApolloClient, InMemoryCache } from '@apollo/client';

const client = new ApolloClient({
 uri: 'https://lnkd.in/gDhXmRBZ', // Replace with your GraphQL API endpoint
 cache: new InMemoryCache()
});

export default client;

Step 3: Wrap Your App with ApolloProvider
Wrap the entire React app with ApolloProvider to make the client available across the application.

// index.js
import React from 'react';
import ReactDOM from 'react-dom/client';
import App from './App';
import { ApolloProvider } from '@apollo/client';

 <ApolloProvider client={client}>
 <App />
 </ApolloProvider>
);

Step 4: Write a GraphQL Query

A query is used to fetch data from the server. Here's a sample query to get a list of users.
query GetUsers {

 id
 name
 email
 }
}

Step 5: Use the Query in a React Component

Use the useQuery hook from Apollo Client to fetch data and display it in a component.

Example: Fetch and Display Users

// Users.js
import React from 'react';
import { useQuery, gql } from '@apollo/client';

// Step a: Write the GraphQL query

const GET_USERS = gql`
 query GetUsers {
 users {
 id
 name
 email
 }
 }
`;

// Step b: Create a React component to fetch and display users
const Users = () => {
 const { loading, error, data } = useQuery(GET_USERS);

 if (loading) return <p>Loading...</p>;
 if (error) return <p>Error: {error.message}</p>;

 return (
 <div>
 <h1>Users</h1>
 <ul>
 {data.users.map(user => (
 <li key={user.id}>
 <p>Name: {user.name}</p>
 <p>Email: {user.email}</p>
 </li>
 ))}
 </ul>
 </div>
 );
};

export default Users;

==>How It Works?
# GraphQL Query: The GET_USERS query requests the id, name, and email fields from the users resource.
# useQuery Hook: The useQuery hook sends the query to the server.
# Loading, Error, Data: Handles loading, error, and displays the data.

==>GraphQL Mutations with React
What is a Mutation?
Mutations are used to create, update, or delete data. For example, adding a new user.

Example: Add a New User
Step 1: Write the Mutation

mutation AddUser($name: String!, $email: String!) {
 addUser(name: $name, email: $email) {
 id
 name
 email
 }
}

Step 2: Use the Mutation in a React Component

Use the useMutation hook to call the mutation on form submission.

// AddUser.js
import React, { useState } from 'react';
import { useMutation, gql } from '@apollo/client';

// GraphQL Mutation
const ADD_USER = gql`
 mutation AddUser($name: String!, $email: String!) {
 addUser(name: $name, email: $email) {
 id
 name
 email
 }
 }
`;

const AddUser = () => {
 const [name, setName] = useState('');
 const [email, setEmail] = useState('');
 const [addUser, { data, loading, error }] = useMutation(ADD_USER);

 const handleSubmit = async (e) => {
 e.preventDefault();
 try {
 await addUser({ variables: { name, email } });
 alert('User added successfully!');
 setName('');
 setEmail('');
 } catch (err) {
 console.error(err);
 }
 };

 return (
 <form onSubmit​={handleSubmit}>
 <h2>Add New User</h2>
 <input
 type="text"
 placeholder="Name"
 value={name}
 onChange​={(e) => setName(e.target.value)}
 />
 <input
 type="email"
 placeholder="Email"
 value={email}
 onChange​={(e) => setEmail(e.target.value)}
 />
 <button type="submit" disabled={loading}>
 {loading ? 'Adding...' : 'Add User'}
 </button>
 {error && <p>Error: {error.message}</p>}
 </form>
 );
};

export default AddUser;

==>How It Works?
# Mutation: The ADD_USER mutation creates a new user with the given name and email.
# useMutation Hook: Calls the mutation when the form is submitted.
# Variables: Inputs for name and email are passed via the variables option in the mutation.

**********************************SOLID Principles**********************************
SOLID Principles in JavaScript & React (With Examples)
-->SOLID principles help make React code scalable, maintainable, and reusable.
  1. Single Responsibility Principle (SRP)
  2. Open/Closed Principle (OCP)
  3. Liskov Substitution Principle (LSP)
  4. Interface Segregation Principle (ISP)
  5. Dependency Inversion Principle (DIP)

==>>>>>>>>>>>>1. Single Responsibility Principle (SRP):
-->A component should have only one responsibility (one reason to change).
Example: Separating UI and Logic
Instead of handling API calls inside a component, separate them:

// Handles only data fetching
const fetchData = async () => {
  const res = await fetch("https://api.example.com/data");
  return res.json();
};

// Handles only UI rendering
const DataList = ({ data }) => (
  <ul>
    {data.map((item) => (
      <li key={item.id}>{item.name}</li>
    ))}
  </ul>
);

// Parent component handles state & lifecycle
const ParentComponent = () => {
  const [data, setData] = React.useState([]);

  React.useEffect(() => {
    fetchData().then(setData);
  }, []);

  return <DataList data={data} />;
};
--> Benefits: Easier to test, debug, and maintain.


==>>>>>>>>>>>>2. Open/Closed Principle (OCP):
-->Components should be open for extension but closed for modification.

-->Example: Extending Button Component with Props Instead of Modifying It.
Instead of creating separate buttons for each type, use props:

const Button = ({ label, onClick, style }) => (
  <button onClick={onClick} style={style}>
    {label}
  </button>
);

// Now we can use the same component in different ways
<Button label="Save" onClick={() => alert("Saved!")} style={{ background: "green" }} />
<Button label="Delete" onClick={() => alert("Deleted!")} style={{ background: "red" }} />

-->Benefits: The Button component is reusable without modification.

==>>>>>>>>>>>>3. Liskov Substitution Principle (LSP):
--> A child component should be usable in place of its parent without breaking functionality.

--> Example:
// Base Component
const Bird = ({ fly }: { fly: () => void }) => {
  return <button onClick={fly}>I can fly!</button>;
};

// Subclass that follows LSP
const Sparrow = ({ fly }: { fly: () => void }) => {
  return <Bird fly={fly} />;
};

// Usage
const App = () => {
  const handleFly = () => alert("Flying high!");

  return (
    <div>
      <Bird fly={handleFly} />
      <Sparrow fly={handleFly} />
    </div>
  );
};

export default App;
--> Sparrow behaves just like Bird, so it's substitutable.
--> Now, Sparrow can replace Bird without breaking functionality. 
--> Ensure props are passed correctly to maintain compatibility.

--> Another example:
const BaseButton = ({ children, ...props }) => (
  <button {...props}>{children}</button>
);

const PrimaryButton = (props) => (
  <BaseButton {...props} style={{ background: "blue", color: "white" }} />
);

const DangerButton = (props) => (
  <BaseButton {...props} style={{ background: "red", color: "white" }} />
);

// Both buttons work without breaking the app
<PrimaryButton onClick={() => alert("Primary Clicked!")}>Primary</PrimaryButton>
<DangerButton onClick={() => alert("Danger Clicked!")}>Danger</DangerButton>
-->Now DangerButton and PrimaryButton is replacable with child component that is BaseButton.
-->Benefits: Components are interchangeable without breaking functionality.


==>>>>>>>>>>>>4. Interface Segregation Principle (ISP):
--> Don't force a component to accept props if it doesn’t need.
--> Here, we separate interfaces so that components only implement what they need.

// Separate interfaces for different functionalities
interface Clickable {
  onClick: () => void;
}

interface Loadable {
  isLoading: boolean;
}

// Button component only needs Clickable
const Button: React.FC<Clickable> = ({ onClick }) => {
  return <button onClick={onClick}>Click Me</button>;
};

// LoadingButton needs both Clickable & Loadable
const LoadingButton: React.FC<Clickable & Loadable> = ({ onClick, isLoading }) => {
  return <button onClick={onClick} disabled={isLoading}>
    {isLoading ? "Loading..." : "Submit"}
  </button>;
};

// Usage
const App = () => {
  return (
    <div>
      <Button onClick={() => alert("Clicked!")} />
      <LoadingButton onClick={() => alert("Submitted!")} isLoading={false} />
    </div>
  );
};

export default App;

-->Why is this correct?
->Button only implements Clickable, not forced to handle isLoading.
->LoadingButton only implements what it needs, keeping concerns separate.

==>>>>>>>>>>>>5. Dependency Inversion Principle (DIP):
-->High-level modules should not depend on low-level modules. Both should depend on abstractions.
-->Example: Using Context API Instead of Directly Passing Props
-->Bad practice: Passing props manually to every component. No abstraction or inversion, high-level components dictate low-level details.
-->Good practice: Use React Context for better abstraction.
-->Prop drilling violates DIP because the high-level components depend on low-level ones to pass data.
-->The parent component directly depends on passing props to child components, making changes harder.
-->Context API follows DIP by inverting dependencies.
  ->Instead of high-level components depending on low-level ones,
  ->Both high- and low-level components depend on abstraction (Context).

Summary:SOLID Principle:
✔ SRP: Separate concerns (UI, logic, API).
✔ OCP: Use props for extensibility.
✔ LSP: Child components should be interchangeable with parents.
✔ ISP: Pass only necessary props.
✔ DIP: Use Context API or dependency injection instead of hardcoding.

Applying SOLID makes React code more maintainable, reusable, and scalable. 

********************Microfrontend using Module federation****************************

-->What is Microfrontend?
Microfrontend (Micro Frontend) is an architectural approach where a large frontend application is broken down into smaller, 
independently deployable modules. Each module is developed, tested, and deployed separately, yet they function together as a unified application. 
This approach is inspired by Microservices on the backend and helps scale frontend development, allowing teams to work independently.

-->There are several ways to implement a microfrontend architecture, depending on how different microfrontends integrate and communicate. 
The most common approaches is: Run-Time Integration (Module Federation)

-->Uses Webpack Module Federation to load microfrontends dynamically at runtime.
-->Each microfrontend is a separate app and can be deployed independently.
-->The container app loads different microfrontends when needed.

-->Pros:
  ->Independent deployment.
  ->Better scalability.

-->Cons:
 ->Version mismatches can occur.
 ->Slightly more complex setup.

-->Explanation of Run-Time Integration using Module Federation (Microfrontend)
What is Module Federation?
Module Federation is a feature in Webpack 5 that allows applications to dynamically import code from other applications at runtime. 
This enables independent deployment of microfrontends without requiring a full rebuild of the host application.

Instead of bundling all microfrontends at build time, Module Federation loads them dynamically, reducing dependencies and improving scalability.

How Module Federation Works?
In a microfrontend architecture using Module Federation, there are typically two main applications:
Host (Shell) Application – The main container that loads microfrontends dynamically.
Remote (Microfrontend) Applications – Independent frontend applications that expose specific modules.
These applications communicate via Webpack's Module Federation Plugin, which allows JavaScript modules to be shared across different builds.

-->Step-by-Step Implementation of Module Federation
Step 1: Install Dependencies
Ensure that your project is using Webpack 5.
npm install webpack webpack-cli webpack-dev-server --save-dev

Step 2: Configure Microfrontend Applications
Each microfrontend (remote app) should be configured to expose components.

Example: Remote Microfrontend (microfrontend1)
webpack.config.js

const { ModuleFederationPlugin } = require("webpack").container;
const path = require("path");

module.exports = {
  mode: "development",
  entry: "./src/index",
  output: {
    publicPath: "http://localhost:3001/",
  },
  devServer: {
    port: 3001,
  },
  plugins: [
    new ModuleFederationPlugin({
      name: "microfrontend1", // Unique name for the microfrontend
      filename: "remoteEntry.js", // The file that exposes modules
      exposes: {
        "./Header": "./src/components/Header", // Exposing a component
      },
      shared: ["react", "react-dom"], // Shared dependencies
    }),
  ],
};
name: Unique identifier for the microfrontend.
filename: The file where modules are exposed.
exposes: Defines which components or modules can be used by other applications.
shared: Defines shared dependencies to avoid duplication.

Step 3: Configure Host (Shell) Application
The host app will load microfrontends dynamically.

Example: Host (container)
webpack.config.js

const { ModuleFederationPlugin } = require("webpack").container;
const path = require("path");

module.exports = {
  mode: "development",
  entry: "./src/index",
  output: {
    publicPath: "http://localhost:3000/",
  },
  devServer: {
    port: 3000,
  },
  plugins: [
    new ModuleFederationPlugin({
      name: "container",
      remotes: {
        microfrontend1: "microfrontend1@http://localhost:3001/remoteEntry.js",
      },
      shared: ["react", "react-dom"],
    }),
  ],
};
remotes: Defines where to load microfrontends dynamically.
The host can now access microfrontend1 from http://localhost:3001/remoteEntry.js.

Step 4: Load Microfrontend Components in Host
In the host app, use React lazy loading to fetch microfrontend components dynamically.

App.js (Host Application)

import React, { Suspense } from "react";

const Header = React.lazy(() => import("microfrontend1/Header"));

const App = () => {
  return (
    <Suspense fallback={<div>Loading...</div>}>
      <Header />
      <h1>Welcome to the Host Application</h1>
    </Suspense>
  );
};

export default App;


Step 5: Run the Applications
Start both applications separately.

Start the Microfrontend (microfrontend1)

npm run start
It will run on http://localhost:3001.

Start the Host Application (container)

npm run start
It will run on http://localhost:3000.

Now, Header from microfrontend1 will be dynamically loaded inside the host application at runtime.

Benefits of Module Federation in Microfrontends
✅ Independent Deployment – Microfrontends can be updated independently without rebuilding the entire app.
✅ Code Splitting – Only the required components are loaded, improving performance.
✅ Shared Dependencies – Reduces bundle size by reusing existing dependencies.
✅ Technology Agnostic – Different teams can use different frontend frameworks.

-->Use Cases for Module Federation:
Large applications with multiple teams working on different features.
Gradual migration from a monolithic frontend to a microfrontend architecture.
Multi-brand or multi-tenant applications requiring independent feature deployment.

Conclusion:
Using Module Federation, microfrontends can be dynamically integrated at runtime, reducing dependencies and improving modularity. 
This approach enables independent development and deployment, making frontend development more scalable and efficient.
